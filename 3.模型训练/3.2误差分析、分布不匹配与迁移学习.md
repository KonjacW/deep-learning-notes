- **核心新增**：
  - 用 `error analysis` 决定优先级
  - 处理 `mislabeled data`
  - 区分 `bias / variance / data mismatch`

# 一、误差分析（Error Analysis）

## 1. 为什么要做

- 当模型离目标还有距离时，可选方向很多：
  - 处理狗图
  - 处理模糊图
  - 处理大猫图
  - 处理滤镜图
- 问题不在于“有没有想法”，而在于：
  - 哪个方向最值得先做
  - 哪个方向提升上限最大

## 2. 基本流程

1. 从开发集里收集一批错误样本
   - 常见做法：抽 100 个误分类样本
2. 人工逐个看
3. 给每个样本打错误类型标签
4. 统计各类错误占比
5. 按占比和可修复性决定优先级

## 3. 核心思想

- 误差分析给出的不是严格最优解
- 而是一个**收益上限估计**

例如：

- 如果 100 个错误样本里只有 5 个是狗
- 那么即使“狗的问题”被完全解决，整体错误也只能减少很小一部分

所以：

- 错误类型占比越高
- 该方向理论提升空间越大

## 4. 典型表格

| 样本编号 | 狗 | 大猫 | 模糊 | 滤镜 | 备注 |
|---|---|---|---|---|---|
| 1 | ✓ |  |  |  | 比特犬 |
| 2 |  |  | ✓ |  | 低清晰度 |
| 3 |  | ✓ | ✓ |  | 雨天动物园 |
| ... | ... | ... | ... | ... | ... |

最后统计每列占比：

- 狗：8%
- 大猫：43%
- 模糊：61%
- 滤镜：12%

## 5. 使用原则

- 同时看 `false positive` 和 `false negative`
- 错误类型可以在分析过程中新增
- 误差分析的价值在于：
  - 快速排优先级
  - 避免在低收益方向浪费几个月

# 二、清理标注错误（Incorrectly Labeled Data）

## 1. 先区分训练集 vs 开发/测试集

- `训练集标签错`
- `开发集/测试集标签错`

这两类问题的重要性不同。

## 2. 训练集标签错误

### 1. 随机错误

- 深度学习对**随机标签错误**通常比较鲁棒
- 如果数据量足够大，且错误近似随机，往往不一定值得优先清理

### 2. 系统性错误

- 如果标签错误有明显模式，就危险得多

例如：

- 总把白色狗标成猫

这会让模型学到系统偏差。

## 3. 开发集 / 测试集标签错误

这里更值得重视，因为：

- 开发集用于选模型
- 测试集用于最终评估

如果标签错误干扰了这两个功能，就应修正。

## 4. 判断是否值得修正

看 3 个量：

1. 总开发集错误率
2. 其中由标签错误导致的错误率
3. 其他真实模型错误率

例如：

- 总错误率：10%
- 其中 6% 的误差样本是标签错
- 则标签错误带来的总体误差约为：

$$
10\% \times 6\% = 0.6\%
$$

此时：

- 标签错影响较小
- 真实模型问题仍占主要部分

但如果模型已优化到：

- 总错误率：2%
- 标签错误仍贡献 0.6%

那么标签问题就占了很大比例，此时更值得清理。

## 5. 修正原则

### 1. dev 和 test 一起修

- 保持同分布
- 不要只修 dev 不修 test

### 2. 理想上应同时检查预测正确和错误的样本

- 否则可能只修“模型输掉的样本”
- 导致评估偏向模型

但现实中：

- 通常只查错分样本
- 因为成本更低

### 3. 不一定要同步修训练集

- dev/test 小，修起来划算
- train 大，且对随机错误更鲁棒
- 所以常见做法是只重点修 dev/test

# 三、快速搭第一个系统，再迭代

## 1. 核心原则

- 新项目开始时，不要一开始就在多个方向深挖
- 更好的做法是：
  - 快速搭出第一个可运行系统
  - 先拿到基线结果
  - 再做误差分析和迭代

## 2. 为什么

因为在真正看见错误之前：

- 你对问题的理解往往不准
- 很多“看起来重要”的方向，实际收益可能很低

## 3. 工程意义

- 原型的价值不只是“先跑起来”
- 更重要的是：
  - 帮你暴露真正瓶颈
  - 给后续优化提供真实反馈

# 四、训练集和开发 / 测试集来自不同分布

## 1. 什么时候会这样做

当你有两类数据：

- 一大批容易获得、但不完全匹配目标场景的数据
- 一小批真正来自目标场景的数据

典型做法：

- 用大量非目标场景数据做训练集
- 用目标场景数据做开发集 / 测试集

## 2. 为什么这么分

因为你真正关心的是：

- 模型在目标场景上的效果

所以：

- `dev/test` 必须贴近真实应用
- `train` 可以更宽松，用来尽量扩大可用训练数据

## 3. 例子

语音激活后视镜任务中：

- 训练集：大量一般语音识别数据
- 开发集 / 测试集：真实车内导航语音数据

这样即使训练分布和目标分布不同，也往往比“只用少量目标数据训练”更好。

# 五、分布不匹配时的偏差与方差分析

## 1. 为什么原来的 bias/variance 分析失效

如果：

- 训练集和开发集同分布

那么：

- `dev error - train error` 主要反映方差

但如果：

- train 和 dev 分布不同

那么这两个误差的差距混入了两种因素：

1. 泛化误差
2. 数据分布差异

所以不能直接把它解释成方差。

## 2. 引入 Training-dev set

新增一个集合：

- `training-dev set`

它的特点：

- 来自训练集同一分布
- 但**不参与训练**

这样就得到 4 类关键误差：

- human-level error
- training error
- training-dev error
- dev error

## 3. 四个误差各自看什么

| 问题类型 | 判断方式 |
| --- | --- |
| 可避免偏差 | $\text{Training Error} - \text{Human-level Error}$ |
| 方差 | $\text{Training-dev Error} - \text{Training Error}$ |
| 数据不匹配 | $\text{Dev Error} - \text{Training-dev Error}$ |
| 是否对 dev 过拟合 | $\text{Test Error} - \text{Dev Error}$ |

## 4. 典型例子

### 例 1

- Human-level：0%
- Train：1%
- Training-dev：9%
- Dev：10%

结论：

- 偏差小
- 方差大
- 数据不匹配小

### 例 2

- Human-level：0%
- Train：1%
- Training-dev：1.5%
- Dev：10%

结论：

- 偏差小
- 方差小
- 数据不匹配大

### 例 3

- Human-level：0%
- Train：10%
- Training-dev：11%
- Dev：12%

结论：

- 可避免偏差大
- 方差小
- 数据不匹配不大

### 例 4

- Human-level：0%
- Train：10%
- Training-dev：11%
- Dev：20%

结论：

- 偏差大
- 方差小
- 数据不匹配也大

## 5. 本质

分布不匹配时，问题从两类变成三类：

- `avoidable bias`
- `variance`
- `data mismatch`

# 六、如何处理数据不匹配（Data Mismatch）

## 1. 先做什么

- 先看开发集错误样本
- 用人工方式理解：
  - 训练集和开发集究竟差在哪

## 2. 常见差异来源

- 背景噪声不同
- 图像清晰度不同
- 场景语义不同
- 特定子任务频率不同

例如语音场景：

- 训练集：安静语音
- 开发集：车内噪音 + 导航地址数字多

## 3. 处理思路

### 1. 收集更像 dev/test 的训练数据

这是最直接也最可靠的方法。

### 2. 人工数据合成（Artificial Data Synthesis）

例如：

- 干净语音 + 汽车噪声
- 合成“车内语音”训练样本

## 4. 人工合成的风险

核心风险：

- **合成数据覆盖面太窄，模型对合成规则过拟合**

例如：

- 只有 1 小时车噪
- 却反复叠加到 10000 小时语音上

人耳听起来可能没问题，但模型可能只学到了这 1 小时噪声模式。

## 5. 结论

- 数据合成有用
- 但前提是：
  - 合成过程足够多样
  - 尽量逼近真实分布
- 本质上，没有特别系统的万能解法，仍要靠：
  - 错误分析
  - 数据理解
  - 有针对性的补数据

# 七、迁移学习（Transfer Learning）

## 1. 基本思想

- 先在任务 $A$ 上学
- 再把学到的知识迁移到任务 $B$

常见做法：

1. 在大数据任务上训练网络
2. 去掉最后输出层
3. 替换成新任务的输出层
4. 在新任务上重新训练

## 2. 两种训练方式

### 1. 只训最后一层或最后几层

- 适合目标数据很少

### 2. 整网微调（fine-tuning）

- 适合目标任务数据较多

## 3. 术语

- `pre-training`：先在大任务上预训练
- `fine-tuning`：再在新任务上微调

## 4. 为什么有效

因为前面层常学到一些通用低层特征：

- 图像中的边缘、纹理、形状
- 音频中的频谱结构、语音模式

这些特征对相关任务通常有迁移价值。

## 5. 什么时候适合

迁移学习通常在以下条件下最有价值：

1. 任务 $A$ 数据很多
2. 任务 $B$ 数据较少
3. 输入形式相同
   - 图像到图像
   - 音频到音频
4. 两个任务底层特征相关

## 6. 不太适合的情况

- 源任务数据并不多
- 目标任务数据反而更多
- 两任务相关性很弱

此时迁移学习可能帮助有限。

# 八、多任务学习（Multi-task Learning）

## 1. 和迁移学习的区别

- `Transfer learning`：先学 A，再迁移到 B，串行
- `Multi-task learning`：一个网络同时学多个任务，并行

## 2. 典型形式

输入一个样本 $x^{(i)}$，输出多个标签：

$$
y^{(i)} \in \mathbb{R}^{k}
$$

例如自动驾驶中：

- 是否有行人
- 是否有车
- 是否有停车标志
- 是否有交通灯

一个样本可以同时有多个正标签，所以这不是 softmax 单标签分类，而是**多标签分类**。

## 3. 损失函数

若共有 $k$ 个任务，则总体损失可写成：

$$
J=\frac{1}{m}\sum_{i=1}^{m}\sum_{j=1}^{k} L(\hat y_j^{(i)}, y_j^{(i)})
$$

其中单个二分类任务常用 logistic loss：

$$
L(\hat y_j^{(i)}, y_j^{(i)})=
-y_j^{(i)}\log \hat y_j^{(i)}
-(1-y_j^{(i)})\log(1-\hat y_j^{(i)})
$$

## 4. 什么时候适合

一般需要：

1. 一组相关任务
2. 共享输入
3. 每个任务都有一定数据
4. 网络足够大，能同时承载多任务

## 5. 特点

- 多任务学习有时能利用任务之间共享表示
- 但实践中整体使用频率低于迁移学习
- 一个比较典型的成功场景是：
  - 计算机视觉中的多物体检测

# 九、端到端学习（End-to-End Learning）

## 1. 定义

- 直接学习从输入 $x$ 到最终输出 $y$ 的映射
- 省掉中间手工设计模块

即：

- 传统流水线：$x \to$ 中间特征 / 子模块 $\to y$
- 端到端：$x \to y$

## 2. 典型例子

### 1. 语音识别

传统方法：

- 手工特征提取
- 音位识别
- 词级拼接
- 文本输出

端到端方法：

- 音频直接到文本

### 2. 机器翻译

- 英文句子直接到法文句子

这是端到端效果较好的代表任务。

## 3. 为什么它吸引人

### 1. 让数据直接说话

- 不强迫模型使用人类预设的中间表示

### 2. 减少手工设计

- 系统结构更统一
- 工程流水线更简化

## 4. 局限

### 1. 往往需要大量数据

如果直接学习的映射很复杂，那么：

- 没有足够的 $(x,y)$ 数据
- 端到端就很难成功

### 2. 可能丢掉有价值的人类先验

- 手工构建的中间模块
- 在小数据场景下可能很有帮助

## 5. 什么时候不一定适合

如果问题能拆成多个更简单的子问题，并且：

- 每个子问题都更容易收集数据
- 或更容易学

那么多步流水线反而可能更强。

### 典型例子

#### 1. 门禁人脸识别

常见更优方案：

1. 先检测人脸位置
2. 再做人脸识别

而不是：

- 整张门禁图像直接识别人身份

#### 2. 手部 X 光估年龄

常见思路：

1. 先分割骨骼 / 测量结构
2. 再根据骨骼特征估年龄

而不是：

- X 光直接到年龄

#### 3. 自动驾驶

更现实的方法通常是：

1. 感知
2. 检测行人 / 车辆 / 障碍物
3. 路径规划
4. 控制

而不是：

- 图像直接输出方向盘角度

## 6. 判断标准

关键问题不是“端到端酷不酷”，而是：

- 你有没有足够多的数据，去直接学习这个复杂映射？

如果答案是否定的：

- 分阶段系统通常更稳妥

# 十、一页总结

| 主题 | 核心问题 | 关键结论 |
|---|---|---|
| Error Analysis | 先改什么最值 | 统计错误类型占比，估计收益上限 |
| Incorrect Labels | 要不要修标签 | train 随机错通常可忍；dev/test 若影响评估应修 |
| Quick Prototype | 项目怎么起步 | 先搭第一个系统，再按错误迭代 |
| Mismatched Distribution | train 和 dev/test 不同怎么办 | dev/test 必须对准目标分布；train 可更宽 |
| Training-dev set | 怎么拆 bias/variance/mismatch | 用 train-dev 把方差和分布差异拆开 |
| Data mismatch | 怎么处理分布差 | 先做错误分析，再补更像 dev 的数据 |
| Transfer learning | 小数据任务怎么借力 | 大任务预训练，小任务微调 |
| Multi-task learning | 多任务能否一起学 | 可共享表示，但使用频率低于迁移学习 |
| End-to-end | 要不要端到端 | 有大数据就强；没大数据时多步法常更实用 |

## 11. 复习抓手

- **误差分析**：不是为了“解释错误”，而是为了排优先级。
- **标签错误**：重点看它是否影响你选模型和评估模型。
- **分布不匹配**：本周最重要的新问题，不能再只用 bias/variance 二分法。
- **Training-dev**：专门用来拆开“泛化问题”和“分布问题”。
- **迁移学习**：大数据任务学表示，小数据任务借表示。
- **多任务学习**：一个网络同时做多件事，本质是共享表示。
- **端到端**：不是默认更高级，前提是有足够多的端到端数据。
- **总原则**：工程上先定位问题来源，再选方法，不要看到工具就直接上。
