# 〇、本周主线

- **目标**：学会设计一套高效的机器学习迭代策略，而不是盲目试方法。
- **核心问题**：当模型效果不好时，应该先改哪一项，怎么判断下一步最值得做。
- **主线框架**：
  - 先定义好要优化的目标
  - 再用合适的开发集 / 测试集对准真实任务
  - 再用偏差 / 方差分析决定优化方向
- **课程基调**：很多团队不是不会训练模型，而是不会设计“正确的迭代系统”。

---

# 一、为什么需要 ML Strategy

## 1. 问题背景

- 搭建深度学习系统时，可尝试的方向很多
- 问题不在于“方法少”，而在于：
  - 不知道哪一步最值得优先做
  - 容易在错误方向上浪费几个月

## 2. ML Strategy 的作用

- 帮你判断：
  - 当前问题是偏差还是方差
  - 应该优先优化训练集表现，还是泛化表现
  - 评估指标是否合理
  - 开发集 / 测试集是否对准真实场景
- 本质上，它是一个**决策框架**，不是某个具体算法。

---

# 二、正交化（Orthogonalization）

## 1. 基本思想

- 理想状态下，尽量让一个调节旋钮只控制一个问题
- 不同问题由不同手段单独处理，互不混淆

## 2. 在机器学习中的对应关系

一个好的系统，最好把下面几件事拆开处理：

1. **先让模型拟合训练集**
   - 解决高偏差
	
2. **再让模型在开发集上泛化好**
   - 解决高方差
	
3. **再让模型在测试集上也稳定**
   - 确认没有对开发集过拟合
	
4. **再保证测试指标真的对应真实业务目标**
   - 实际部署情况

# 三、单一数字评估指标

## 1. 为什么需要单一数字

- 如果每次比较模型都要看一堆指标，团队决策会很慢。
- 深度学习常常依赖快速试验和快速迭代，因此需要一个**单一数字指标

## 2. 作用

- 便于快速排序多个模型
- 便于统一团队优化目标
- 便于判断“这次改动到底有没有更好”

## 3. 典型例子

### 1. Precision 和 Recall

这时常用：

$$
F_1 = \frac{2PR}{P+R}
$$

其中：

- $P$ 是 precision
- $R$ 是 recall

`F1 score` 把两者合成一个数，更方便比较。

### 2. 多地区误差合并

如果系统在多个地区分别测试：

可以定义总体平均误差：

$$
\text{Average Error}=\frac{1}{n}\sum_{i=1}^n e_i
$$

这样模型比较更直接。

## 4. 工程意义

- 单一指标不一定完美
- 但它能显著提高团队迭代速度
- 在项目早期，**能快速比较** 往往比“指标设计极其精细”更重要

# 四、Satisficing 与 Optimizing 指标

## 1. 核心思想

很多任务不止一个指标，这时常见做法不是把所有指标都同时最大化，而是：

- 选一个 `optimizing metric` 作为主优化目标
- 其余指标设为 `satisficing metric`，只要求达到门槛

## 2. 为什么这样做

- 如果多个指标都想“尽可能最好”，选择模型会很困难
- 改成：
  - 一个主目标
  - 多个约束条件
- 决策就会清晰很多

## 3. 例子

### 1. 猫分类器

- 优化目标：准确率最大
- 满足条件：运行时间不超过 100ms


### 2. 唤醒词系统

- 优化目标：唤醒词检测率尽可能高
- 满足条件：误触发次数每天不超过一次

## 4. 本质

这相当于把问题写成：

$$
\max \text{Performance}
$$

subject to

$$
\text{Constraint}_1 \le c_1,\quad \text{Constraint}_2 \le c_2,\dots
$$

虽然课程里不写成严格优化问题，但工程思想就是这样。

# 五、开发集与测试集的设计

## 1. 关键原则

- **开发集（Dev set）和测试集（Test set）必须来自同一分布

## 2. 开发集 / 测试集的真正作用

- `Dev set`：帮助你做决策，决定往哪个方向优化
- `Test set`：最后一次评估，估计模型真实泛化能力

## 3. 典型错误

### 1. 训练集多源混合，但 dev/test 不一致

例如：

- 训练集：网页高质量图片 + 用户手机上传图片
- 开发集：网页图片
- 测试集：手机上传图片

这样会出问题，因为你调参方向是根据网页图片选的，但最终考核却看手机图片。

### 2. 目标分布选错

如果真实业务是：

- 用户上传的模糊手机图

但你用的数据却主要是：

- 网页上的高清猫图

那么即使测试分数很高，也不代表系统真的对产品有用。

# 六、开发集和测试集大小

## 1. 传统比例不再绝对适用

- 70% train / 30% test
- 60% train / 20% dev / 20% test

## 2. 现代深度学习中的常见原则

- 训练集尽量大
- 开发集和测试集只要足够评估即可

例如：

- 总数据 100 万
- dev 1 万
- test 1 万
- train 98 万

## 3. 为什么 dev/test 可以相对小

因为它们的主要用途不是训练，而是：

- 稳定比较模型
- 给出最终性能估计

只要样本量足够让结论有统计意义，就不需要占太大比例。

---

# 七、什么时候该改变开发集、测试集或指标

## 1. 改变的标准

常见两类情况：

1. **评估指标不对**
2. **开发集 / 测试集分布不对**

## 2. 指标不对的例子

假设做猫分类器，模型把色情图片误判成猫。

如果你的错误率指标把这类错误与普通错误一视同仁，可能会出现：

- 指标上看模型更好了
- 但真实产品体验更差了

这时应修改指标，比如：

- 对某类严重错误加更高权重

可写成加权误差：

$$
\text{Weighted Error}=\frac{1}{m}\sum_{i=1}^m w_i \cdot \mathbf{1}[\hat y^{(i)} \ne y^{(i)}]
$$

其中：

- $w_i$ 表示样本重要性权重

## 3. 数据分布不对的例子

假设产品真实场景是：

- 用户上传的模糊图片

但 dev/test 用的是：

- 网页高清图片

这时应重新构造 dev/test，让它更贴近最终应用。

## 4. 原则

- 不要执着于“保持历史可比性”
- 如果原来的目标就设错了，应及时修正
- 正确的目标比连续可比更重要

# 八、为什么要用人的表现作参考

## 1. 原因

在很多感知任务上：

- 图像识别
- 语音识别
- 自然语言理解中的部分任务

深度学习的表现接近甚至超过人类。

因此，人类水平表现（human-level performance）就成了一个重要参照物。

## 2. 它的价值

### 1. 作为 Bayes error 的近似

对很多自然感知任务，人类已经很强，因此：

- 最强人类表现常被用来近似 `Bayes error`

虽然不严格相等，但实践中常够用。

### 2. 帮助判断偏差和方差

如果知道：

- human-level error
- train error
- dev error

就能更清晰地判断：

- 是否还有明显可避免偏差
- 是否主要是方差问题

### 3. 帮助判断进展空间

- 如果模型离人类还很远，通常还有很大提升空间
- 如果模型已逼近甚至超过人类，再继续提升往往更难

---

# 九、可避免偏差（Avoidable Bias）

## 1. 定义

即：

$$
\text{Avoidable Bias} \approx \text{Train Error} - \text{Human-level Error}
$$

这里的人类水平常作为 Bayes error 的近似，代表训练中产生的误差

## 2. 为什么它重要

因为训练误差本身高，不一定就说明问题严重，关键要看和“理论可达到的水平”差多远。

## 3. 诊断方式

### 1. 看偏差

比较：

- `Train error`
- `Human-level error`

如果差距大，说明偏差大。

### 2. 看方差

比较：

- `Dev error`
- `Train error`

如果差距大，说明方差大。

## 4. 例子

### 情况 A

- Human-level error：1%
- Train error：8%
- Dev error：10%

分析：

- 可避免偏差：$8\%-1\%=7\%$
- 方差：$10\%-8\%=2\%$

结论：

- 主要问题是偏差大
- 应优先提升训练集拟合能力

### 情况 B

- Human-level error：7.5%
- Train error：8%
- Dev error：10%

分析：

- 可避免偏差：$8\%-7.5\%=0.5\%$
- 方差：$10\%-8\%=2\%$

结论：

- 偏差不大
- 主要问题变成方差

这说明：

- **同样的 train/dev error**
- 因为 human-level error 不同
- 对问题的判断会完全不同

# 十、如何理解“人的表现”

## 1. 人的表现不是一个固定数字

不同参照标准会给出不同的人类水平：

- 普通人
- 受过训练的人
- 领域专家
- 多位专家投票 / 集体判断

## 2. 该选哪一种

如果你是把 human-level performance 当作 Bayes error 的近似，那么通常应选：

- **最强的、最相关的人类水平**

因为它更接近理论上限。

## 3. 为什么要谨慎

如果你选了偏弱的人类基准，会误以为：

- 模型已经很接近极限

但实际上可能还差很远。

# 十一、什么时候能超过人类水平

## 1. 结构化数据任务更容易超过人类

例如：

- 在线广告点击率预测
- 商品推荐
- 风险评分
- 大规模表格数据建模

原因：

- 人类不擅长直接处理高维大规模结构化数据
- 机器可以从海量样本中学到更细致的模式

## 2. 自然感知任务更难超过人类

例如：

- 图像识别
- 语音理解
- 一些复杂语言理解任务

因为人在这些任务上本来就很强。

## 3. 超过人类后的变化

一旦模型超过人类水平，很多原本好用的方法会变弱：

- 人工标注的参考价值下降
- 人工 error analysis 不再那么可靠
- 不容易再靠“人来告诉你正确答案”获得明显提升方向

因此：

- 接近人类水平前，很多技巧有效
- 超过后，优化难度通常会上升

# 十二、如何系统改善模型表现

## 1. 总体思路

先诊断，再下药，不要乱试。

## 2. 如果是高可避免偏差

说明模型连训练集都没学好，优先提高拟合能力。

可尝试：

- 更大的网络
- 训练更久
- 更好的优化算法
  - Momentum
  - RMSprop
  - Adam
- 更好的网络结构
- 更合适的超参数

## 3. 如果是高方差

说明训练集学得还行，但泛化差。

可尝试：

- 获取更多数据
- 正则化
- Dropout
- 数据扩增
- 调整网络结构
- 超参数搜索

## 4. 核心逻辑表

| 现象                                   | 主要判断   | 优先方向        |
| ------------------------------------ | ------ | ----------- |
| Train error 高，且远高于 human-level error | 高可避免偏差 | 提升拟合能力      |
| Train error 不高，但 Dev error 明显更高      | 高方差    | 提升泛化能力      |
| 指标提升但真实体验变差                          | 指标设计错  | 重设 metric   |
| Dev 表现好但 Test/真实场景差                  | 数据分布错  | 重设 dev/test |
|                                      |        |             |

# 十三、一页总结

| 主题                        | 核心问题          | 关键结论                          |
| ------------------------- | ------------- | ----------------------------- |
| ML Strategy               | 下一步该做什么       | 先诊断，再优化                       |
| Orthogonalization         | 一个方法是否只解决一个问题 | 好系统应尽量分开控制                    |
| Single-number metric      | 怎么快速比较模型      | 用单一数字提高迭代速度                   |
| Satisficing vs Optimizing | 多指标怎么决策       | 一个主目标，其余设门槛                   |
| Dev/Test design           | 应该对准什么分布      | dev/test 必须对准真实目标且同分布         |
| Human-level performance   | 为什么参考人类       | 常用作 Bayes error 近似            |
| Avoidable bias            | 怎么区分偏差和方差     | train-human 看偏差，dev-train 看方差 |
| Improvement strategy      | 怎么提升效果        | 偏差和方差要分治                      |

## 14. 复习抓手

- **策略课的重点不是新算法，而是“怎么决定先做什么”。**
- **正交化**：一个旋钮最好只管一个问题。
- **评估指标**：能快速排序模型，比面面俱到更重要。
- **Satisficing / Optimizing**：一个主目标，其他做约束。
- **Dev/Test**：要代表最终要解决的问题，而不是手头最容易拿到的数据。
- **Human-level error**：是判断可避免偏差的重要参照。
- **诊断公式**：
  - 偏差看 `Train error - Human-level error`
  - 方差看 `Dev error - Train error`
- **工程原则**：不要盲目堆方法，先判断瓶颈在哪。
